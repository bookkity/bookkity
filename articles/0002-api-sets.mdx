# Introduction

Microsoft introduced the concept of API sets with the release of Windows 7 and expanded their implementation in Windows 8. This initiative aimed to modularize the operating system, making it more flexible and portable. The effort was driven by Microsoft's interest in supporting a broader range of platforms beyond traditional PCs.

Here's what the official documentation says about them: 

> All versions of Windows share a common base of operating system (OS) components that's called the core OS (in some contexts this common base is also called OneCore). In core OS components, Win32 APIs are organized into functional groups called API sets.
> 
> The purpose of an API set is to provide an architectural separation from the host DLL in which a given Win32 API is implemented, and the functional contract to which the API belongs. The decoupling that API sets provide between implementation and contracts offers many engineering advantages for developers. In particular, using API sets in your code can improve compatibility with Windows devices.

Which sounds pretty cool so far but there's an issue. Microsoft needed to introduce a way to support this new concept without breaking existing software.

They needed to:
- Allow linking against umbrella libraries (e.g. OneCore.lib), which internally reference api-ms-sth DLLs.
- Support linking against original libraries like kernel32.dll.

At the same time, they wanted the flexibility to implement functions wherever needed.

# Analysis

Let's start by taking a look at the good old `kernel32.dll`. We can see lots of function with `Stub` suffix, what's going on here? 

![alt](/article/0002/kernel32-stubs.png)

Let's pick one at random and find out. I'll choose `GetLastError` without any particular reason behind it. 

We can see that it's exported as `GetLastError`, without the `Stub` suffix and that it does nothing besides calling `__imp_GetLastError`. The name didn't lie, it's really just a stub.

![alt](/article/0002/kernel32-get-last-error-stub.png)

What's `__imp_GetLastError` though? We haven't seen that function yet. Let's take a peek.

![alt](/article/0002/kernel32-api-ms-win-core-errorhandling-imports.png)

It seems to be part of imports from `api-ms-win-core-errorhandling-l1-1-0.dll`. There's no actual implementation of `GetLastError` in `kernel32.dll`. Seems like it's one of those functions they wanted to move somewhere else.

Well, what are we waiting for? Let's take a look at `api-ms-win-core-errorhandling-l1-1-0` but first we need to find it. 

Where is it? This particular one is located in `C:\Windows\System32\downlevel`, which is where most of those `api-ms-` libraries are found, though it's not a strict rule. Some may be located elsewhere.

![alt](/article/0002/c-windows-system32-downlevel.png)

Also, I'll mention as a side note that DLL loading order still applies here. When an application requests a DLL, Windows follows a specific search order to locate it. This includes checking the application's directory first, then system directories, and finally any paths listed in the environment variables. So in the case below, Windows will first try to search for the relevant DLLs in the application directory.

![alt](/article/0002/league-api-sets.png)

The first thing we'll see after opening `api-ms-win-core-errorhandling-l1-1-0` is that there are no symbols whatsoever. That's concerning.

![alt](/article/0002/api-ms-win-core-errorhandling-l1-1-0-symbols.png)

But there are exports! Let's take a look at them.

![alt](/article/0002/api-ms-win-core-errorhandling-l1-1-0-exports.png)

Uh oh. There's something called a `forwarder` and they all seem to be pointing back at `kernel32`! That's infinite recursion, isn't it? What the heck is going on here?

It turns out those libraries are special. They are not supposed to be treated like most other libraries. You'll never resolve functions by doing so. Instead, there's a mapping of those empty API set libraries to actual libraries with real implementations.

This mapping is created at boot according to `Windows/System32/apisetschema.dll` and additional schemas defined in `Computer/HKEY_LOCAL_MACHINE/SYSTEM/CurrentControlSet/Control/Session Manager/ApiSetSchemaExtensions`.

![alt](/article/0002/schema-extensions-in-registry.png)

Each of them has a section called `.apiset`, which defines how those API set libraries are translated to actual libraries.

![alt](/article/0002/apisetschema-strings.png)

After creation, the mapping resides in the PEB or process environment block. Let's take a look what the documentation says about it.

![alt](/article/0002/peb-documentation.png)

That's... a lot of reserved fields and nothing that looks like an api set mapping. Documentation will unfortunately not help us here. We'll have to dig deeper. Let's take a look at what WinDbg says. 

![alt](/article/0002/windbg-peb.png)

There's an `ApiSetMap` at `0x68` (which is `reserved9[0]`). That sounds like what we are looking for. Unfortunately, there are no symbols for it. They were present before but got removed. As of right now, the structure looks more or less like this:

`ApiSetHeader` is what's present at `PEB->ApiSetMap`. There's also a `ApiSetHeader->Count` of `ApiSetHashEntry` at `PEB->ApiSetMap + ApiSetHeader->HashEntriesOffset` and an unspecified amount of `ApiSetNamespaceEntry` at `PEB->ApiSetMap + ApiSetHeader->NamespaceEntriesOffset`.

Hashes are computed by initializing the value to zero, multiplying it with each step by the hash multiplier (`ApiSetHeader->HashMultiplier`) and then adding the ordinal value of the lower case character. An example implementation of this algorithm is as follows:

```cpp
#include <ctype.h>

#define WIN32_LEAN_AND_MEAN
#include <Windows.h>

static DWORD CalculateHash(const PWSTR string, const DWORD length, const DWORD hashMultiplier) {
    DWORD hash = 0;

    for (auto i = 0; i < length; i++) {
        hash *= hashMultiplier;
        hash += tolower(String[i]);
    }

    return hash;
}
```

<Alert type={'tip'}>
    `ApiSetHashEntry` entries are sorted by hash in ascending order.
</Alert>
