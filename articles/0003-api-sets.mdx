# Introduction

Microsoft introduced the concept of API sets with the release of Windows 7 and expanded their implementation in Windows 8. This initiative aimed to modularize the operating system, making it more flexible and portable. The effort was driven by Microsoft's interest in supporting a broader range of platforms beyond traditional PCs.

Here's what the official documentation says about them:

> All versions of Windows share a common base of operating system (OS) components that's called the core OS (in some contexts this common base is also called OneCore). In core OS components, Win32 APIs are organized into functional groups called API sets.
>
> The purpose of an API set is to provide an architectural separation from the host DLL in which a given Win32 API is implemented, and the functional contract to which the API belongs. The decoupling that API sets provide between implementation and contracts offers many engineering advantages for developers. In particular, using API sets in your code can improve compatibility with Windows devices.

Which sounds pretty cool so far but there's an issue. Microsoft needed to introduce a way to support this new concept without breaking existing software.

They needed to:
- Allow linking against umbrella libraries (e.g. OneCore.lib), which internally reference api-ms-sth DLLs.
- Support linking against original libraries like kernel32.dll.

At the same time, they wanted the flexibility to implement functions wherever needed.

# Analysis

Let's start by taking a look at the good ol' `kernel32.dll`. We can see lots of functions with the `Stub` suffix, what's going on here?

![alt](/article/0002/kernel32-stubs.png)

Let's pick one at random and find out. I'll choose `GetLastError` without any particular reason behind it.

We can see that it's exported as `GetLastError`, without the `Stub` suffix and that it does nothing besides calling `__imp_GetLastError`. The name didn't lie, it's really just a stub.

![alt](/article/0002/kernel32-get-last-error-stub.png)

What's `__imp_GetLastError` though? We haven't seen that function yet. Let's take a peek.

![alt](/article/0002/kernel32-api-ms-win-core-errorhandling-imports.png)

It seems to be part of imports from `api-ms-win-core-errorhandling-l1-1-0.dll`. There's no actual implementation of `GetLastError` in `kernel32.dll`. Seems like it's one of those functions they wanted to move somewhere else.

Well, what are we waiting for? Let's take a look at `api-ms-win-core-errorhandling-l1-1-0`, but first we need to find it.

Where is it? This particular one is located in `C:\Windows\System32\downlevel`, which is where most of those `api-ms-` libraries are found on PCs, though it's not a strict rule. Some may be located elsewhere.

![alt](/article/0002/c-windows-system32-downlevel.png)

Also, I'll mention as a side note that DLL loading order still applies here. When an application requests a DLL, Windows follows a specific search order to locate it. This includes checking the application's directory first, then system directories, and finally any paths listed in the environment variables. You can see this being used below.

![alt](/article/0002/league-api-sets.png)

The first thing we'll see after opening `api-ms-win-core-errorhandling-l1-1-0` is that there are no symbols whatsoever. That's concerning.

![alt](/article/0002/api-ms-win-core-errorhandling-l1-1-0-symbols.png)

But there are exports! Let's take a look at them.

![alt](/article/0002/api-ms-win-core-errorhandling-l1-1-0-exports.png)

Uh oh. There's something called a `forwarder` and they all seem to be pointing back at `kernel32`! That's infinite recursion, isn't it? What the heck is going on here?

It turns out those libraries are special. They are not supposed to be treated like most other libraries. You'll never resolve functions by doing so. Instead, there's a mapping of those empty API set libraries to actual libraries with real implementations.

This mapping is created at boot according to the `Windows/System32/apisetschema.dll` and also some additional schemas defined in `Computer/HKEY_LOCAL_MACHINE/SYSTEM/CurrentControlSet/Control/Session Manager/ApiSetSchemaExtensions`.

![alt](/article/0002/schema-extensions-in-registry.png)

Each of them has a section called `.apiset`, which defines how those API set libraries are supposed to be translated to the actual libraries.

![alt](/article/0002/apisetschema-strings.png)

After creation, the mapping resides in the PEB (process environment block). Let's take a look what the documentation says about it.

![alt](/article/0002/peb-documentation.png)

That's... a lot of reserved fields and nothing that resembles the mappings we are looking for. The documentation will unfortunately not help us here. We'll have to dig deeper. Let's take a look at what WinDbg says.

![alt](/article/0002/windbg-peb.png)

There's an `ApiSetMap` at `0x68` (which is `reserved9[0]`). That sounds like what we are looking for. Unfortunately, there are no symbols for it. They were present around Windows 7 but got removed later. As of right now, the structure looks more or less like this:

```cpp
#define WIN32_LEAN_AND_MEAN
#include <Windows.h>

struct ApiSetHeader {
    DWORD Version;
    DWORD Size;
    DWORD Flags;
    DWORD Count;
    DWORD NamespaceEntriesOffset;
    DWORD HashEntriesOffset;
    DWORD HashMultiplier;
};

struct ApiSetHashEntry {
    DWORD Hash;
    DWORD IndexInEntriesNamespace;
};

struct ApiSetNamespaceEntry {
    DWORD Flags;
    DWORD NameOffset;
    DWORD SizeOfApiSetName;
    DWORD SizeOfApiSetNameEx; // without hyphens
    DWORD ValueEntriesArrayOffset;
    DWORD HostsNumber;
};

struct ApiSetValueEntry {
    DWORD Flags;
    DWORD NameOffset;
    DWORD NameLength;
    DWORD ValueOffset;
    DWORD ValueLength;
};
```

`ApiSetHeader` is what's present at `PEB->ApiSetMap`. There's also a `ApiSetHeader->Count` of `ApiSetHashEntry` at `PEB->ApiSetMap + ApiSetHeader->HashEntriesOffset` and an unspecified amount of `ApiSetNamespaceEntry` at `PEB->ApiSetMap + ApiSetHeader->NamespaceEntriesOffset`.

To resolve a library, we first need to compute it's hash, which is done as follows:

```cpp
#include <ctype.h>

#define WIN32_LEAN_AND_MEAN
#include <Windows.h>

static DWORD CalculateHash(const PWSTR string, const DWORD length, const DWORD hashMultiplier) {
    DWORD hash = 0;

    for (auto i = 0; i < length; i++) {
        hash *= hashMultiplier;
        hash += tolower(String[i]);
    }

    return hash;
}
```

where `string` is it's name without the extension (so `api-ms-win-security-base-ansi-l1-1-0`, not `api-ms-win-security-base-ansi-l1-1-0.dll`), and `hashMultiplier` is `ApiSetHeader->HashMultiplier`.

After we've computed the hash, we can perform a look-up. There are three arrays we'll have to use — hash entries, namespace entries and value entries. All of them are located relative to `peb->ApiSetMap`. We get the offset of the first one from `ApiSetHeader->HashEntriesOffset` and the offset from the second one from `ApiSetHashEntry->IndexInEntriesNamespace`.

At this point, we're able to loop through all records, and display their names:

```cpp
int main()
{
    const auto *teb = reinterpret_cast<ThreadEnvironmentBlock*>(NtCurrentTeb());
    const auto *peb = teb->ProcessEnvironmentBlock;

    size_t map_address = reinterpret_cast<size_t>(peb->ApiSetMap);
    const auto *header = static_cast<ApiSetHeader*>(peb->ApiSetMap);

    const auto *hash_entries = reinterpret_cast<ApiSetHashEntry*>(map_address + header->HashEntriesOffset);
    const auto *namespace_entries = reinterpret_cast<ApiSetNamespaceEntry*>(map_address + header->NamespaceEntriesOffset);

    for (size_t hash_entry_idx = 0; hash_entry_idx < header->Count; ++hash_entry_idx)
    {
        const auto *hash_entry = hash_entries + hash_entry_idx;
        const auto *namespace_entry = namespace_entries + hash_entry->IndexInEntriesNamespace;

        std::wstring_view input_wide_name { reinterpret_cast<wchar_t*>(map_address + namespace_entry->NameOffset), namespace_entry->SizeOfApiSetName / 2 };
        std::string input_name { input_wide_name.begin(), input_wide_name.end() };

        std::print("{}\n", input_name);
    }

    return 0;
}
```

<Alert type={'tip'}>
    `ApiSetHashEntry` entries are sorted by hash in ascending order, which allows implementations to perform binary search on them.
</Alert>

Great, what's next? It seems like we are on the right track.

Now we have to make use of the last array. We get its offset from `ApiSetNamespaceEntry->ValueEntriesArrayOffset`, this time there isn't a single array for the entire map — each namespace entry has its own. The numbers of elements is located in `ApiSetNamespaceEntry->HostsNumber`. The majority of libraries only has one "host", but there are some with multiple ones:

```
api-ms-win-core-io-l1-1-1 -> kernel32.dll
api-ms-win-core-io-l1-1-1 -> kernelbase.dll
api-ms-win-core-processthreads-l1-1-7 -> kernel32.dll
api-ms-win-core-processthreads-l1-1-7 -> kernelbase.dll
api-ms-win-core-appinit-l1-1-0 -> kernel32.dll
api-ms-win-core-appinit-l1-1-0 -> kernelbase.dll
api-ms-win-core-util-l1-1-1 -> kernel32.dll
api-ms-win-core-util-l1-1-1 -> kernelbase.dll
api-ms-win-core-processsecurity-l1-1-0 -> kernel32.dll
api-ms-win-core-processsecurity-l1-1-0 -> kernelbase.dll
ext-ms-win-kernel32-errorhandling-l1-1-0 -> kernel32.dll
ext-ms-win-kernel32-errorhandling-l1-1-0 -> faultrep.dll
```

When we combine all of this into:

```cpp
int main()
{
    const auto *teb = reinterpret_cast<ThreadEnvironmentBlock*>(NtCurrentTeb());
    const auto *peb = teb->ProcessEnvironmentBlock;

    size_t map_address = reinterpret_cast<size_t>(peb->ApiSetMap);
    const auto *header = static_cast<ApiSetHeader*>(peb->ApiSetMap);

    const auto *hash_entries = reinterpret_cast<ApiSetHashEntry*>(map_address + header->HashEntriesOffset);
    const auto *namespace_entries = reinterpret_cast<ApiSetNamespaceEntry*>(map_address + header->NamespaceEntriesOffset);

    for (size_t hash_entry_idx = 0; hash_entry_idx < header->Count; ++hash_entry_idx)
    {
        const auto *hash_entry = hash_entries + hash_entry_idx;
        const auto *namespace_entry = namespace_entries + hash_entry->IndexInEntriesNamespace;

        const auto *value_entries = reinterpret_cast<ApiSetValueEntry*>(map_address + namespace_entry->ValueEntriesArrayOffset);

        std::wstring_view input_wide_name { reinterpret_cast<wchar_t*>(map_address + namespace_entry->NameOffset), namespace_entry->SizeOfApiSetName / 2 };
        std::string input_name { input_wide_name.begin(), input_wide_name.end() };

        for (size_t value_entry_idx = 0; value_entry_idx < namespace_entry->HostsNumber; ++value_entry_idx)
        {
            const auto *value_entry = value_entries + value_entry_idx;

            std::wstring_view output_wide_name { reinterpret_cast<wchar_t*>(map_address + value_entry->ValueOffset), value_entry->ValueLength / 2 };
            std::string output_name { output_wide_name.begin(), output_wide_name.end() };

            if (namespace_entry->HostsNumber > 1)
                std::print("{} -> {}\n", input_name, output_name);
        }
    }

    return 0;
}
```
